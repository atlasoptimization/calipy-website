Hosted executionNo public inference API or hosted MCP endpoint is offered by this website.

The public package is usable through Python. Model Forge, the newer block API, and the optional agent bridge are development previews. Do not infer that an API exists in the installed package from a preview shown here.

Start with a reproducible Python workflow.

  1. Record the installed package version and inspect its actual public API. Use its matching documentation.
  2. State the scientific quantities, observation process, priors, and dimension roles before writing a model.
  3. Build the smallest complete example and check it against known or simulated data.
  4. Select an inference method supported by that interface and model. Retain diagnostics and distinguish point estimates from posterior uncertainty.
  5. Present the assumptions, code, and limitations to the person making the scientific decision.

These are suggested scientific working practices. Repository instructions and the user’s authorization remain the authority for the actual task.

Step 2 / Proposal

The agent proposes a model you can review.

Illustrative agent response

“I suggest one shared offset, a Normal prior, and a Normal measurement law. I am treating the reference and noise scale as known. Should reference uncertainty or drift be included?”

Review the quantities, connections, and assumptions in the model. The local development bridge can expose model descriptions and submit bounded proposals through the existing authoring operations.

reference + offset → measurement law → readings

A proposal may be revised or rejected. An accepted edit does not establish that the model is scientifically adequate.

Step 3 / Execution

You authorize the work that should run.

You

“The assumptions are sufficient for this teaching example. Use the agreed observations and inference settings, then return the result and its checks.”

Reviewing a model and authorizing execution are separate actions. The development integration can prepare a reviewed inference plan and execute a specifically authorized stored plan. Broader automation and remote deployment remain development work.

For real work, the run budget, permitted data, and requested checks should be part of the brief.

Step 4 / Handoff

The agent returns evidence you can inspect.

Example handoff format

“The offset is approximately +0.45 °C under the agreed model. The report includes the data and model revision, inference settings, posterior summary, comparison with the analytic reference, and limits of the calibration.”

This is illustrative dialogue built around the executed sensor-offset lesson, not a transcript of a provider-backed agent run. A useful real handoff should contain:

  • The question, assumptions, model revision, and data used.
  • The method, settings, diagnostics, and retained results.
  • What the estimate supports and which checks are missing.
  • A suggested next measurement or model change for your review.

With the appropriate scopes, the local development bridge exposes retained results and reporting. You remain responsible for the scientific decision.

How agent-assisted modeling works.

The development workflow connects your agent host to CaliPy’s existing model operations. A useful interaction has a concrete brief, a reviewable proposal, and a report tied to the model and result.

  1. You set the question.Describe the instrument, data, unknown quantities, and the decision the result should inform.
  2. The agent inspects the model.Scoped model descriptions and scientific interfaces give it context for a proposal.
  3. You review the proposed change.Inspect the affected objects and assumptions before accepting changes to the project.
  4. You authorize a specific run.Accepting a model or inference plan does not itself grant execution permission. Available execution remains separately scoped.
  5. The agent returns an inspectable report.With the appropriate permissions, it can retrieve retained results and generate reports. Ask for the model revision, assumptions, method, diagnostics, and limitations alongside the answer.

Current scope: local development integration, bounded model operations, and explicitly authorized result access and execution. The broader agent-driven service is still being developed; a provider-backed end-to-end scientific workflow has not been established by this website demo.

Your agent host and AI provider remain your choice. CaliPy’s ordinary Python and GUI workflows do not automatically start an AI provider.

LOCAL DEVELOPMENT PROTOTYPE

An optional bridge for agent-assisted modeling.

The development checkout contains a separately packaged, optional stdio MCP bridge. It exposes a bounded set of model inspection, proposal, review, reporting, and explicitly scoped execution operations over existing CaliPy contracts.

Users supply their own agent host. Starting ordinary CaliPy does not start an AI provider. Model changes and execution have distinct review and permission boundaries.

Availability: the companion bridge is not published to a package registry and this site exposes no remote MCP endpoint. Configuration must come from the supplied development checkout and its current instructions. Do not guess a server URL or an installation command.

Provider-backed end-to-end workflows and broader automation remain development work. A local bridge prototype is not a claim of an autonomous hosted calibration service.
